# forge-kit

**A governance harness for AI-assisted repositories.** Rules about what must be true before work
starts and after it lands, enforced by a build failure rather than a note asking nicely.

forge-kit is not a collection of clever agents. It started as one, and the agents turned out to be
the least distinctive thing in it: the tree today carries 28 prose components against 24 guard
scripts and 35 contract test suites, and the last six phases of work produced guards, versioning
discipline, install scope and measurement rather than new capability. What is left that nobody else
ships is the outer loop, and that is what this is for.

## What forge-kit answers, and what its neighbours answer

Three projects, three different questions. The fastest way to decide what you need is to ask which
one you have.

| Question | Answered by | For example |
|---|---|---|
| **How should this work be done?** | [superpowers](https://github.com/obra/superpowers), installed as `superpowers@claude-plugins-official` | brainstorming, writing-plans, test-driven-development, systematic-debugging, requesting-code-review, verification-before-completion |
| **What tool does this specific task?** | [anthropics/claude-plugins-official](https://github.com/anthropics/claude-plugins-official), 292 plugins, and community collections such as [wshobson/agents](https://github.com/wshobson/agents) | code-review, pr-review-toolkit, claude-security, code-simplifier, hookify; tdd-workflows, error-diagnostics, comprehensive-review |
| **What must be true before work starts, and after it lands?** | **forge-kit** | the ticket gate and its standard, the template lockstep, the version and semver guards, the leak guard, governed overnight runs, release enforcement, host awareness, roadmap phases |

The line forge-kit holds itself to: **superpowers owns the inner loop, forge-kit owns the outer.**
The inner loop is how work happens. The outer loop is what must be true on either side of it. Where
the two touch, forge-kit gives way, and since #177 that is a build failure rather than an intention.

## Start here

Install the outer loop first. It is the part with no counterpart anywhere, and it works whether or
not you use anything else.

```bash
claude plugin marketplace add agigante80/forge-kit
claude plugin install forge-kit-governance@forge-kit    # brings forge-kit-devops with it
```

Restart Claude Code, then gate your first ticket with `/gate-ticket <N>`.

Everything else is optional and can be added one group at a time. If you would rather be told what
fits your project than choose from a list, install the recommender instead and run it:

```bash
claude plugin install forge-kit-adapt@forge-kit
```

Then say "run forge-adapt" in your project, or invoke `/forge-kit-adapt:adapt`.

`claude plugin list` shows what you have and at which version;
`claude plugin uninstall <group>@forge-kit` reverses any of it.

**A group installed at user level is inert until a project asks for it.** The components that ACT
gate themselves on something the project owns: `roadmap-phases` does nothing without a
`docs/roadmap.md`, the `block-dashes` hook stays dormant until a project creates `.claude/no-dashes`,
and the overnight guard arms only when a run's manifest exists. Installing a group is not a
commitment to using it everywhere.

**Two groups declare a dependency.** `forge-kit-governance` and `forge-kit-roadmap` both need
`forge-lib.sh` from `forge-kit-devops`, and both declare it, so a fresh install pulls it in and says
so. If you are UPDATING a group you already had, see the upgrade note under
[Keeping up to date](#keeping-up-to-date).

## Scenarios

**Given** a repository with no governance and Claude Code installed,
**when** you install `forge-kit-governance` and run `/gate-ticket 42` on an issue filed against an
older template,
**then** missing GWT scenarios and test specs are synthesised from the current template, the verdict
is PASS, NEEDS-WORK or BLOCKED with a concrete change list and never a score, and the review is
posted to the forge so the reasoning outlives the session.

**Given** you want only rolling wave planning,
**when** you run `claude plugin install forge-kit-roadmap@forge-kit`,
**then** `forge-kit-devops` arrives with it because the dependency is declared,
**and** in every project without a `docs/roadmap.md` the group stays inert.

**Given** you would rather be advised than choose,
**when** you run forge-adapt,
**then** you get a project profile, a ranked recommendation per category with a reason under sixty
characters, and nothing is written until you approve,
**and** each approved component is registered by enabling its plugin group rather than copied into
your repository.

**Given** superpowers is installed,
**when** forge-adapt runs,
**then** `code-simplifier` is suppressed with its reason shown rather than hidden, `closing-sessions`
is recommended with the memory split stated, and outer-loop components are recommended unchanged,
**and** you can still install a suppressed component after the conflict is repeated back to you.

**Given** a neighbouring marketplace ships an agent with the same name as one of ours,
**when** forge-adapt decides,
**then** it says so and explains the difference rather than silently recommending a second copy,
**but** it does not suppress ours on a name match alone, because three projects ship a
`code-reviewer` and they are three different agents.

**Given** your team uses Cursor, Copilot, or no AI CLI at all,
**when** you copy the issue templates, `.github/labels.yml` and `docs/guides/ticket-standards.md`,
**then** every ticket is filed against one standard and any agent can check a ticket against that
document, because it is canonical rather than a summary,
**but** nothing enforces it for you: the gate, the hooks and the drift detection need Claude Code.

**Given** groups installed some weeks ago,
**when** you run `forge-adapt drift`,
**then** each installed component is compared against the library by version marker, a stale
marketplace checkout is reported, and nothing is written,
**and** acting on it means `marketplace update` then `update` per group, because registration tracks
this repository and pulls nothing.

**Given** a repository moving off GitHub to self-hosted Forgejo,
**when** the `github-to-forgejo` cutover runs,
**then** components call `forge_*` instead of `gh`, host detection is per repository, and a repo
with no Forgejo config behaves exactly as before,
**and** `block-legacy-host-push` is installed project-locally so it can never fire anywhere else.

**Given** a repository whose history contains home paths and personal names,
**when** the pre-commit hook runs,
**then** the public scan runs first, before every early exit, and blocks on a home-path shape or a
reachable email address,
**and** the private scan redacts the name it matched, because a failing hook's output is the pasted
text it exists to police,
**and** a machine with no name list is told loudly that names are not being checked rather than
passing quietly.

**Given** a queue of gated tickets and nobody present,
**when** `working-overnight` runs,
**then** work ships as branch-plus-PR and never merges,
**and** at the review trip wire the loop defers rather than deciding for you, parks the item with
its stopping data, and leads the morning report with it.

**Given** a project that grew a component forge-kit does not have,
**when** you run `forge-adapt contributions`,
**then** project-only components are surfaced, domain-specific ones filtered out, and contribution
issues opened for the rest.

## Where forge-kit overlaps its neighbours

Stated here rather than left to be discovered, and measured rather than asserted:
`scripts/neighbour-manifest.sh --refresh` regenerates `docs/neighbours.tsv` from the marketplaces
installed on a machine, and `scripts/check-neighbour-overlap.sh` fails the build on a duplicate.

**forge-kit's specialist agents share an ancestor with `wshobson/agents`.** Five of them had barely
moved since, so #178 retired them rather than maintaining a fork nobody had changed:

| Retired from forge-kit | Install this instead |
|---|---|
| `tdd-orchestrator`, `test-automator`, `performance-engineer` | `tdd-workflows@claude-code-workflows`, `performance-testing-review@claude-code-workflows` |
| `backend-architect` | `backend-development@claude-code-workflows` |
| `backend-security-coder` | `data-validation-suite@claude-code-workflows` |
| `/pr-enhance` | `comprehensive-review@claude-code-workflows` |
| the whole `forge-kit-backend` group, 5 skills | `backend-development@claude-code-workflows` |

One duplicate stays and `.neighbour-allow` records why: `architect-review` is dispatched by name
from `/full-review`, and pointing that at a plugin we do not ship would fail silently when absent.

What remains that shares a NAME with a neighbour is six collisions, where two projects picked the
same obvious name and the files are 103 to 529 lines apart. Claude Code namespaces subagent types by
plugin, so nothing collides in practice.

**The counter-example is what this kit is for.** `/full-review` comes from the same ancestor as
wshobson's `comprehensive-review` and has diverged by 173 lines. What diverged is the **iteration
contract**: round accounting, the trip wire, bad-fix injection. Eleven references in ours, none in
the original. That is outer-loop discipline added to an inner-loop tool.

## The governance layer without Claude Code

Four artifacts here are portable, and they are the ones that carry the rules:

| Artifact | What it gives you |
|---|---|
| `.github/ISSUE_TEMPLATE/` | Six templates carrying GWT scenarios, unit and E2E test specs, personal-data handling, a security checklist and documentation impact |
| `.github/labels.yml` | The label taxonomy that routes issues, applied by `sync-labels.sh`, which never deletes a label it does not recognise |
| `docs/guides/ticket-standards.md` | **The canonical rules**, not a summary. The gate is only allowed to restate it in enumerated places, and `check-restatements.sh` fails the build if the two disagree. Any agent that can read markdown can hold a ticket to it. |
| The shell assets | Ten of them, bash 3.2 compatible with no package manager, so they run in any CI |

Copy those into your project and any AI, or none, can work to the same standard.
**[docs/guides/without-claude-code.md](docs/guides/without-claude-code.md) is the entry point**: what
to copy, what you can run, real output from the mechanical gate, and what you do not get.

**Be clear about what you do not get.** Nothing enforces any of it for you. The gate, the hooks, the
size budget and the drift detection are Claude Code components, and there is no adapter for another
CLI. "AI-agnostic at the governance layer" means the YAML and the markdown are not Claude-specific,
which is a property of file formats rather than a feature. The governance layer takes no dependency
on the `claude` CLI, deliberately and by rule, which is what keeps that door open.

A root `AGENTS.md`, the cross-agent instruction format, points at `CLAUDE.md` for any agent working
ON this repository.

## What forge-adapt does

1. **Analyses your project:** stack files, CLAUDE.md, source structure, existing `.claude/` contents
2. **Recommends components:** ranked, with a reason each, and with anything your neighbours already
   cover suppressed or flagged
3. **Waits for your approval:** nothing is written until you choose
4. **Installs what you approved.** Most components are **registered**, by enabling the plugin group
   they live in: they resolve what they need at runtime, so they own no file in your repository that
   could drift, duplicate or clobber. A component is **copied and adapted** into `.claude/` only
   when it must be: when it declares `scope: project`, when you installed from a bare clone with no
   marketplace, or when it is a hook, which reaches a project by its own route. An adapted copy is
   rewritten against your profile, so "check for SQL injection" becomes "check for Prisma
   `$queryRaw` injection in `src/db/`".

Secondary modes: `forge-adapt drift` reports what is behind and writes nothing; `forge-adapt
refresh <name>` deep-compares one component and merges in what it is missing while preserving your
adaptation; `forge-adapt contributions` surfaces project-only components worth contributing back;
`forge-adapt templates` audits issue templates and can install the template governance.

## When to run what

Hand-written on purpose: this is sequencing guidance, not inventory.

| When | Run | Why |
|---|---|---|
| Before writing code for a ticket | `/gate-ticket <N>` | A ticket that fails the gate costs a rewrite; one that passes carries its own GWT scenarios and test specs. |
| While implementing | `code-reviewer` | The per-task reviewer, under the bounded iteration contract. Not `/full-review`. |
| Before merging, or periodically | `/full-review` | Multi-lens audit. Findings enter the bounded loop or become tickets. |
| When CI is red | `/ci-health` | Files P0 tickets for failures and auto-fixes the safe classes. |
| Periodically | "audit dependencies", "health check" | `dep-auditor` and `health-check` are agents, not slash commands: mention them in conversation. |
| Before a session ends | `closing-sessions` | Persists durable facts and resume state; without it the next session starts cold. |
| When a ticket is stalled on a decision | `decision-brief` | Re-gates it, costs the options, and rewrites the body so the decision can be made from it. |
| Opening or closing a phase | `/phase` | Only with `forge-kit-roadmap` installed. Inert in a project with no roadmap. |
| Every few months | `forge-adapt drift` | Reports what lags forge-kit and whether the marketplace copy itself is stale. Writes nothing. |

Overnight work is its own mode: `working-overnight` runs governed unattended cycles that ship
branch-plus-PR and never merge, deferring decisions that are yours rather than guessing.

## Keeping up to date

**Adding the marketplace tracks this repository, but nothing pulls it for you.** There is no
auto-update and no daemon, so an installed group stays at the version you installed until you say
otherwise. This repository's own maintainer ran four minor versions behind for weeks while
developing against the tree, which is why it is stated here rather than left implied.

```bash
claude plugin marketplace update forge-kit    # refresh the local copy of this repo
claude plugin update forge-kit-governance     # move an installed group onto it
```

`claude plugin update` takes one group at a time, so repeat it for each group you have. Restart
Claude Code afterwards; the CLI says so on each update.

**Upgrade note for `forge-kit-governance` and `forge-kit-roadmap`.** Both declare a dependency on
`forge-kit-devops`, and a dependency is resolved when a plugin is INSTALLED, never when it is
updated. If you already had one of them and you update it, it will report `failed to load` until you
run this once:

```bash
claude plugin install forge-kit-devops@forge-kit
```

The error names that command, so you will not have to remember it.

**On a manual install**, `git -C ~/forge-kit pull` is the equivalent. Clone with
`git clone https://github.com/agigante80/forge-kit ~/forge-kit`, then run forge-adapt from your
project: it finds the clone and works from there, adapting components into `.claude/` rather than
registering them, because there is no marketplace to register with.

## Related project

[**vibe-coding-prompts**](https://github.com/agigante80/vibe-coding-prompts) is the same author's
other answer to the same problem, from the opposite end. It is 14 versioned, platform-agnostic
meta-prompts you paste into any assistant (Claude, ChatGPT, Gemini, Copilot Chat), where forge-kit
is components installed into a project. Neither depends on the other and they overlap in subject
rather than in mechanism.

Take that one if you have no AI CLI, or several, and want the knowledge without the plumbing. Take
this one if you want rules that fail a build. Two mechanisms here were borrowed from it outright:
the generated, CI-verified index (#96) and the version-bump gate this repo now runs on every push.
